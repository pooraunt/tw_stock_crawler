# 台股爬蟲：新增或重構一個資料集

這個專案把台股資料爬下來、清理後存進 `db/` 的 SQLite。每種資料一支爬蟲模組（`.py`），GUI 介面全部集中在 `main_twstock_crawler.pyw`。

資料怎麼清理，**唯一的依據是 [docs/通用資料清理規則.md](../../../docs/通用資料清理規則.md)**，
每次動手前重讀一次；這份 skill 不重複規則內容，只講「怎麼做事」。

## 與使用者合作的方式

這幾點是使用者在歷次工作中反覆要求的，比任何技術細節都重要：

- **先討論，聽到「開始」才動手。** 使用者會說「先討論」「沒說開始不要動」。討論階段只做唯讀的事：讀檔、`SELECT`、少量試抓網址。不建立、不修改任何檔案與資料庫。
  使用者只回答了部分問題時，剩下的問題再問一次，不要自行假設後開工。
- **討論階段做了什麼要講清楚。** 回報開頭先說明「只做了唯讀檢查，沒動任何檔案」，
  並列出讀了哪些檔、試抓了哪些網址。曾有一次只是讀檔，被誤會成執行了程式。
- **不動舊程式，另外生成新檔。** 重構時舊檔保留；要比較兩種版本時存成另一個檔名。
  這個資料夾不是 git 倉庫，覆寫就沒有備份。
- **資料不輕易刪。** 舊資料表、舊資料庫預設保留，要刪要搬都先問；使用者常選擇自己手動處理。
- **不確定就問**，尤其是欄位要不要留、資料代表什麼意思。使用者比你懂台股資料，
  例如股票名稱結尾的 `*` 曾被誤判為網站標記，其實是重要資訊。
- 退役的檔案移到 `old_data/`，不直接刪除。

## 流程

### 1. 了解現況（唯讀）

- 重讀規則檔。
- 有舊程式就讀舊程式：它存了哪些欄位、存到哪裡、有哪些已經壞掉的地方。
- 讀一支性質最接近的現有模組當範本（見 [references/module-anatomy.md](references/module-anatomy.md) 的對照表）。
- 查 [references/sources.md](references/sources.md)：這個來源以前有沒有踩過坑。
- 需要比對現有資料時，用唯讀方式開資料庫（`sqlite3.connect('file:db/x.db?mode=ro', uri=True)`）。

### 2. 實際試抓來源

不要只憑印象描述來源，抓幾份真實資料來看，用量控制在十次請求上下：

- 取一個最近的期別、一個最早的期別（確認資料起點與早年格式是否不同）、一個不存在的期別
  （假日、尚未公布），看來源各回什麼。
- 逐檔爬的資料，挑幾種不同性質的個股：一般股、金融股、ETF（`0050`、`00679B`）、
  特別股（`2881A`）、上櫃股，看哪些沒有資料。
- 找有沒有「一次回傳全市場」的彙總來源，優先於逐檔爬。
- 留意規則沒涵蓋的值（新的缺值符號、新的日期樣式），記下來放進討論。
- 沒有實測、只是憑印象的部分，回報時要明講。

### 3. 提出討論

一次把需要決定的事列完，每項附上建議與理由，讓使用者可以逐點回覆或說「照建議」：

1. **實測發現**：資料起點、連線狀況、缺值與特殊值、是否有重複代碼。
2. **欄位命名對照表（R-19）**：每一個要存的欄位都列，不可只列部分。格式見下方。
   `sid`、`sname`、`date` 固定用英文；其餘沿用舊程式命名，或用精簡的中文名。
3. **建議不存的欄位（R-18）**：欄位名稱、範例值、不存的理由，由使用者決定。
   規則 R-15 明列的欄位可直接刪，其餘不得自行刪除。
4. **命名與存放**：程式檔名、資料庫檔、資料表名、主鍵、log 檔名。
   現有的配置見 [references/project-map.md](references/project-map.md)，新資料優先放進性質相符的現有資料庫。
5. **範圍與行為**：歷史資料要回溯多遠（早年格式不同時，建議只支援現行格式）、
   重爬時覆蓋或保留歷次版本、來源沒有資料的個股怎麼處理、舊資料表怎麼處理。
6. **會直接照慣例做的部分**也列出來，讓使用者有機會反對。

R-19 對照表格式：

| #   | 來源欄位名稱 | 資料庫 field name | 型別                           | 範例值      | 備註      |
| --- | ------ | -------------- | ---------------------------- | -------- | ------- |
| 1   | （原始名稱） | （精簡且可識別）       | TEXT / INTEGER / REAL / DATE | （真實抓到的值） | 單位、轉換方式 |

上市與上櫃的來源欄位名稱不同時，各列一欄。

### 4. 撰寫

使用者說「開始」之後才寫。照 [references/module-anatomy.md](references/module-anatomy.md) 的結構寫，
寫法、註解密度、命名都跟現有模組一致。幾個不能省的原則：

- **所有來源都成功才存檔。** 上市、上櫃（或同一天的多份報表）任何一份失敗，該期別整個不存，避免資料庫裡出現只有一半的期別。
- **無法解析的值不可靜默略過**（R-14）：丟錯或寫進 log。重複的主鍵要報錯，不自動去重。
- **來源給什麼就存什麼**（R-17）：不推算、不補值。上市沒有的欄位不替它用其他欄位算出來。
- 規則沒涵蓋的情況，先問使用者，同意後在規則檔對應章節新增條文，並登記在最後的「規則異動紀錄」；
  其他模組若有同樣的處理（例如各模組的 `NA_SYMBOLS`），一併檢查是否要跟著改。

### 5. 測試

- **在暫存資料庫或資料庫副本上測**，不寫入 `db/` 的正式資料庫，除非使用者同意。
  作法：測試腳本裡把模組的 `DB_PATH` 指到暫存資料夾（scratchpad）內的檔案。

- 至少測這幾種情況：正常期別、重爬同一期別（不產生重複列）、沒有資料的期別、
  逐檔爬取時來源沒有資料的個股、中途停止後接續。

- 拿一兩檔熟悉的個股（如 2330、1301）跟來源網頁核對數字。

- 跑入庫前檢查（取代人工逐項核對規則檔第 5 節的清單）：
  
  ```bash
  python .claude/skills/tw-crawler-dataset/scripts/check_db.py <資料庫路徑> <資料表>
  ```
  
  月資料加 `--monthly`（檢查日是否為 10）；資料表沒有主鍵時用 `--key sid,date` 指定檢查重複的欄位。
  「錯誤」要修到沒有；「警告」（如金額為負）列給使用者人工確認。

- 全市場的完整爬取通常要數十分鐘，留給使用者自己從 GUI 執行，不要代跑。

### 6. 接上 GUI

新資料集要在 `main_twstock_crawler.pyw` 加一個頁面或併入現有頁面（例如每日資料是在 `DAILY_SETS` 加一列）。
介面的作法另見 `tw-crawler-gui` skill。

### 7. 回報

- 新增、修改了哪些檔案；哪些舊檔沒動。
- 測試結果要有數字（幾筆、哪一天），並**明講沒測到的部分**，例如
  「GUI 只確認能開啟，沒有實際按開始」「完整 1,988 檔沒有跑過，時間是估的」。
- 與舊程式行為不同的地方、順手多做的改動，逐項列出。
- 測試時若在正式資料庫或 log 留下了資料，要說明留下了什麼。
- 還需要使用者決定的事放在最後。
